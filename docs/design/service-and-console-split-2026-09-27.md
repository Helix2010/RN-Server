# 接口拆成三个服务、控制台拆成两个（2026-09-27）

> 状态：设计已定（用户 2026-09-27 确认第 7 节三个问题都按建议做），按第 6 节分两步实施。
> 相关：[console-accounts-external-maintenance-2026-09-27.md](console-accounts-external-maintenance-2026-09-27.md)（账号由外部系统维护、只剩统一登录）。

## 1. 用户的决定（2026-09-27）

1. **接口拆成三个服务**：平台端、租户端、App 端。
2. **管理端拆成两个**：租户控制台、平台控制台。平台控制台用 **platform.anyfun.win**。
3. **拆完之后，平台管理员不能操作任何租户**，只能操作平台自己的功能。
4. **打包机和签名闸的接口归平台端**。
5. **三个服务共用同一个库**，不按服务分数据库账号。

实现方式（我的建议，用户没有异议）：**同一个仓库、同一个二进制，按角色起三个进程**，不拆成三套代码。三个服务共用库表、迁移、租户解析和发布与配置的模型；拆成三个仓库，就得复制模型或抽共享库并保持版本同步，迁移归谁跑也会变成问题。扫链已经是这样做的（`rn-server indexer`）。控制台同理：同一个仓库出两份构建。

## 2. 现状

- 一个 `rn-server` 进程承担全部接口：
  - App 约 31 条：`/v1/mobile`、`/v1/public`、`/v1/ota`、`/app/*`、`/.well-known`；
  - 租户管理约 107 条：`/v1/admin/*` 里按域名认租户的那部分；
  - 平台管理 44 条：`/v1/admin/platform/*`；
  - 打包机与签名闸约 40 条：`/v1/build-agent`、`/v1/signer`、`/v1/machine-setup`。

  打包任务回收、推送派发两个后台任务也在这个进程里。
- nginx：
  - `api.<租户域名>` 全部转给 13080；
  - `console.<租户域名>` 的 `/v1/` 也转给 13080，并把 Host 改写成这个租户的 `api.*`；
  - `/auth/v1/` 转给认证中心。
- 控制台只有一份构建。平台页靠插件的「平台专用」标记在租户会话里隐藏。平台管理员要管某个租户，就打开那个租户的控制台域名：当前租户由域名决定。
- 打包机和签名闸配置的服务地址是 `https://api.anyfun.win`。

## 3. 三个服务

### 3.1 角色

同一个二进制，子命令选角色：`rn-server app`、`rn-server tenant`、`rn-server platform`。
- 每个角色只注册自己的路由。App 服务里根本没有 `/v1/admin`，从 `api.*` 碰不到管理接口。
- 三个角色都有 `/health/*`。
- 不带子命令时保持现在的行为（一个进程承担全部），只给过渡与本地开发用，生产不再这样起。

### 3.2 路由归属

| 服务 | 路由 | 端口 |
| --- | --- | --- |
| App 端 | `/v1/mobile/*`、`/v1/public/*`、`/v1/ota/*`、`/app/*`、`/.well-known/*`、`/docs`、`/openapi.json` | 13081 |
| 租户端 | `/v1/admin/*`，平台那部分除外；租户控制台的统一登录（`/v1/admin/auth/*`、`/client/v1/oauth/login`） | 13082 |
| 平台端 | `/v1/admin/platform/*`；平台控制台的统一登录；打包机与签名闸：`/v1/build-agent/*`、`/v1/signer/*`、`/v1/machine-setup/*` | 13080（沿用） |

平台端沿用 13080，是因为 amos 上的签名闸直接连 `http://127.0.0.1:13080`（`SIGNER_SERVER_URL`，不经 nginx）。这样签名闸一个配置都不用改。
端口用命令行参数给（`rn-server app --port 13081`），写在各自的 unit 里；不能用 unit 里的 `Environment=PORT=`，因为 `EnvironmentFile` 里的 `PORT=13080` 会覆盖它。

**直连端口的自动化要跟着改**：amos 上用管理密钥发 OTA 的脚本直连 `127.0.0.1:13080`，带 `Host: api.anyfun.win` 调 `/v1/admin/ota/*`。第一步上线后这些租户接口在租户端，要改成连 13082；平台接口仍是 13080。

后台任务：打包任务回收、推送派发放在平台端，各只有一份。扫链保持单独的进程。

迁移：保持单独的 `rn-foundation-migrate`。部署时先迁移，再启动三个服务。

### 3.3 进程内的状态

各服务各管各的，不需要共享：
- 二次验证码：属于会话，一个会话只对一个服务；
- 注册、邀请、诊断上报的限流：只在 App 端；
- 发测试邮件的计数：只在平台端；
- 租户解析与机器登记的缓存：都来自库，每个进程各缓存一份。

### 3.4 nginx

| 域名 | 路径 | 转给 |
| --- | --- | --- |
| `api.<租户域名>` | `/v1/build-agent/`、`/v1/signer/`、`/v1/machine-setup/` | 平台端（机器配置的地址不变，不用改任何一台机器） |
| `api.<租户域名>` | 其余 | App 端 |
| `console.<租户域名>` | `/v1/`、`/client/v1/oauth/login` | 租户端（Host 改写照旧） |
| `console.<租户域名>` | `/auth/v1/` | 认证中心（不变） |
| `platform.anyfun.win` | 静态文件 | 平台控制台的构建产物 |
| `platform.anyfun.win` | `/v1/`、`/client/v1/oauth/login` | 平台端 |
| `platform.anyfun.win` | `/auth/v1/` | 认证中心（与租户控制台同一套转发和限流） |

systemd 三个 unit：`rn-foundation-app`、`rn-foundation-tenant`、`rn-foundation-platform`，同一个 EnvironmentFile，各自覆盖端口。部署脚本 `rn-foundation-apply` 要改成重启三个服务。按 `deploy/amos/README.md` 的约定，CI 只比对这个脚本的 sha256，不能自己更新它，要用户在 amos 上重跑 `setup-ci-deploy.sh`。

## 4. 两个控制台

### 4.1 租户控制台（console.<租户域名>）

- 只有租户自己的页面，也就是现在所有不带「平台专用」标记的插件。
- 只收租户会话：统一登录回调只认这个租户的记录。平台管理员在这里登录会得到 `no_access`。
- 按「是不是平台会话」切换只读的 6 个页面，统一成租户视角，处理方式见第 5 节。打包仓库目录、预测平台关联在这里只读显示。

### 4.2 平台控制台（platform.anyfun.win）

- **页面**：
  - 平台管理员、控制台成员（跨租户只读，按租户分组）、统一登录、邮件发送；
  - 打包机与签名闸、签名闸恢复密钥、Apple 证书与密钥（含按租户的只读总览）；
  - 扫链管理、钱包与设备查询和封禁（平台风控）；
  - 平台推送默认、平台发布存储默认（含 CORS 汇总）；
  - 租户打包目录、外部系统关联（第 7 节第 1、2 条）。
- **不按租户**：没有「当前租户」，也没有租户切换，因为决定 3 不许平台操作租户。
- **只收平台会话**：统一登录回调只认平台记录。
- **构建**：同一个仓库，Vite 两个入口，各自只注册自己的插件，共用设计系统与请求层。

### 4.3 平台端的统一登录不依赖租户

现在统一登录的发起与回调挂着 `domainTenantScope`：先按域名认出租户，再把租户 id 放进流程 Cookie 的加密附加数据。platform.anyfun.win 不是任何租户的域名。所以平台端的发起与回调改用固定的附加数据（`auth-cid:flow:platform`），回调地址和退出地址直接用 platform.anyfun.win。认证中心的 `{baseHost}` 方式不用改，但要在认证中心给 RN 应用登记 `platform.anyfun.win` 这个回调域名。那是写 `auth_server` 库，写之前先问。

### 4.4 会话

- 两个服务都用 `admin_sessions`。
- 平台端只认 `tenant_id` 为 NULL 且账号是 `scope='platform'` 的会话；租户端只认租户会话，平台会话一律当没登录。
- Cookie 本来就按域名隔开：`console.*` 和 `platform.anyfun.win` 各是各的。

## 5. 平台会话在租户接口上的特权怎么处理

决定 3 之后，租户端不再有平台会话。原来按「是不是平台会话」分支的地方：

| 位置 | 原来平台会话多了什么 | 拆完之后 |
| --- | --- | --- |
| 打包任务视图 `build_jobs.go` | 看得到是哪台机器领的 | 租户端一律按租户视角（不给机器名）。平台端在「打包机与签名闸」里看机器正在做什么 |
| 签名闸同步提示 `keystore_generation.go` | 列出签名闸名字 | 租户端只说有几台 |
| iOS 交付 `ios_delivery.go` | 同一个 Apple Team 还有哪些租户 | 租户端只给「还有别人在用」这个布尔值 |
| 审计 `listAudit` | 平台视角的字段 | 租户端只给租户视角；平台端看平台级审计（`tenant_id=0`） |
| 签名密钥视图 `build_keystore.go` | 平台视角 | 租户端只给租户视角 |
| 推送凭据 `push_credentials*.go` | 能改、删继承自平台的默认凭据 | 平台默认只在平台控制台的「平台推送默认」里改；租户只能覆盖成自己的 |
| 发布存储 `release_storage.go` | 能改继承自平台的存储；拿全平台的 CORS 并集 | 平台默认存储与 CORS 并集挪到平台控制台；租户只能覆盖、只看自己的 |
| 预测平台探测 `/predict/probe` | 只有平台会话能调 | 跟着第 7 节第 2 条走 |
| 打包仓库目录 `build_config.go` | 只有平台能改 `repoDirectory` | **第 7 节第 1 条** |
| 预测平台关联 `services.predict` | 只有平台能改（scopeId 指向别的租户就会显示别人的市场） | **第 7 节第 2 条** |
| 控制台成员列表 `/tenant-accounts` | 只有平台管理员能看当前租户的成员 | **第 7 节第 3 条** |

## 6. 分两步实施

### 第一步：接口拆进程（不改接口路径、不改控制台）

- **服务端**：
  - 加三个角色子命令，路由按第 3.2 节分开注册；
  - 平台端带两个后台任务；
  - 测试覆盖「每个角色只有自己的路由」。
- **部署**：
  - 三个 systemd unit；
  - nginx 按第 3.4 节分流（这一步还没有 platform.anyfun.win）；
  - `rn-foundation-apply` 改成重启三个服务。
- **过渡期**：平台管理员仍在租户控制台上操作。`/v1/admin/platform/*` 由 nginx 转给平台端，会话在库里，两个服务都认，所以这一步对使用者无感。
- **上线顺序**：
  1. 合并后 CI 先部署新二进制。这时 amos 上还是旧的 `rn-foundation-apply` 和 `rn-foundation-server`，新二进制不带子命令时承担全部接口，行为不变。
  2. 用户在 amos 上以 root 跑 `deploy/amos/service-split-switch.sh`。它会备份、拿部署锁，装三个 unit 与新的 `rn-foundation-apply`，起三个进程，换 nginx，再经 nginx 逐项核对分流；核对通过才删旧 unit，任何一步失败都自动退回。新的 `rn-foundation-apply` 由它顺带装上，sudoers 不变，不用重跑 `setup-ci-deploy.sh`。
  3. 切换前脚本先核对二进制认不认角色子命令。旧二进制会忽略参数，在 13080 上起全量进程。
- **数据库连接**：`MYSQL_CONNECTION_LIMIT` 按进程算。amos 上每个进程 3 条，API 三个进程加扫链最多 12 条，原来是 6 条。

### 第二步：平台控制台独立

- **上线前要准备好的**：
  - Cloudflare 上 platform.anyfun.win 的 DNS；
  - 宿主机网关加这个 SNI（网关在宿主机上，要管网关的人做）；
  - 源站证书覆盖到这个域名；
  - amos nginx 加 server 块；
  - 认证中心登记回调域名（写 `auth_server`，先问）。
- **控制台**：两份构建；平台控制台的插件与页面按第 4.2 节，部署到 `/opt/rn-foundation/admin/platform`。
- **服务端**：
  - 租户端不再认平台会话，第 5 节的特权分支删掉；
  - 平台端的统一登录按第 4.3 节改；
  - 平台默认的推送与存储、CORS 并集挪到平台端。
- **顺序**：平台控制台先上线并验收（平台管理员能在 platform.anyfun.win 登录、做平台维护），再上线「租户端不认平台会话」。反过来的话，中间有一段平台管理员哪里都进不去。

两步都不改 `go.mod`，也不碰打包机的构建输入（`cmd/build-agent`、`signing/*`），打包机不用重签。

## 7. 已确认（2026-09-27，都按建议做）

1. **打包仓库目录（`repoDirectory`）**：平台控制台加一张「租户打包目录」平台级配置表（租户 → 目录），不进入任何租户。值仍存在各租户的 `build.android` 里（复用现有存储，打包任务读取的地方不变），只有平台端的这张表能改；租户端一律只能原样带回。
2. **预测平台关联（`services.predict`：接口域名、scopeId、链、端点）**：平台控制台加一张「外部系统关联」平台级登记表（租户 → 预测平台的 scopeId 等），租户只能看、不能改。理由：scopeId 写错就会让 App 显示别人的市场，而 RN 没有办法验证某个 scopeId 属于哪个租户。值仍存在各租户 `mobile-bootstrap` 的 `services` 段（下发给 App 的地方不变）；探测接口（`/predict/probe`）挪到平台端。
3. **跨租户、只读的视图保留**：控制台成员列表（按租户分组）、Apple 证书与密钥的按租户总览。钱包与设备的跨租户查询和封禁也保留，属于平台风控。
