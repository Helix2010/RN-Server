# ADR-0021：租户控制台账号与统一登录（ChainUp 认证中心）

状态：Accepted（2026-09-26）

完整设计：`docs/design/tenant-console-accounts-and-sso-2026-09-25.md`（下称「设计」）；表与配置：`docs/database/ADMIN_ACCOUNTS_SCHEMA.md`；接口：`contracts/openapi.json`。

## 背景

控制台只有一个账号（环境变量 `ADMIN_USERNAME`），同时是平台管理员。签名材料、推送凭据要改由租户自己交，前提是租户有自己的控制台账号。用户 2026-09-25 决定：租户账号接公司的统一认证（ChainUp 认证中心，OAuth2 授权码 + PKCE，不是 OIDC），RN 与 pm-cup 各登记一个应用；账号流程是「先用本系统账号登录 → 必须绑定统一认证账号 → 之后只走统一认证」；先不分角色；应急账号与 TOTP 后续再做。2026-09-26：开发期用自建在 dev1 上的认证中心（公网入口 `login.dexfun.win`，集中登录域名方式）。

## 决策

1. **新建 `tenant_admin_accounts`**，会话表加 `tenant_id` / `account_id` / `login_method`。平台管理员仍是环境变量那一个，不进账号表。
2. **会话分平台 / 租户**：
   - 租户会话只在请求域名属于同一个租户时有效，否则当没登录；
   - 每个请求回表查账号状态，停用立即生效；
   - 租户会话永远不是平台管理员（`platformAdminRequest`），不再只看用户名。
3. **改状态的管理请求，Origin 必须与请求域名属于同一个租户**（以前任何租户域名都算可信来源）。`CORS_ORIGINS` 里显式配置的来源照旧放行。
4. **成员由平台管理员在当前域名的租户下添加**：生成 16 位初始口令，只显示一次，72 小时有效；可以停用、解绑并重置。操作都进审计，审计不含口令。
5. **待绑定账号只能查会话、登出、走绑定**，其余 403 `BIND_REQUIRED`。
6. **统一登录**：
   - 客户端配置放在 `app_configs` 平台级 `auth.cid`，密钥用 `secretbox` 加密；
   - 发起状态（state、PKCE、mode、target、回调地址）与「待确认的绑定」都放在 `secretbox` 加密的 Cookie 里，不落库；
   - 回调路径是认证中心固定的 `/client/v1/oauth/login`。
7. **绑定必须本人确认**：
   - 回调只记下「要绑哪个统一认证账号」，本人在控制台确认之后才落库，落库时本地口令作废；
   - 绑定只能从这个待绑定账号的已登录会话发起，确认时再核对一次会话（防绑定 CSRF）。
   - 2026-09-26 起，确认还要带发到统一认证账号邮箱的验证码（防绑错），见 ADR-0022。
8. **不自动开户**：统一认证账号在这个租户下没有已绑定的账号，一律拒绝。
9. **控制台域名**：
   - nginx 转发 console.* 时把 Host 改写成 api.*，所以控制台域名从 `X-RN-Console-Host` 头取；
   - 服务端核对这个头与 Host 属于同一个租户，不一致就用 Host；
   - api.* 上关掉统一登录的发起与回调。

## 后果

- 上线要改 amos 的 nginx（`deploy/amos/nginx-*.inc`、`nginx-rn-foundation.conf`），并在认证中心登记每个租户的 `https://console.<租户域名>/client/v1/oauth/login`。
- **TOTP 敏感操作再验证与设计 §3.4 的租户接口审计还没做**，给真实租户开放账号之前必须补齐。在那之前，租户账号能看到和操作本租户控制台里的一切，包括导出签名密钥密文、下载 .ipa。
- 认证中心不可用时租户账号登不进来；平台账号不受影响。应急账号后续再加。
