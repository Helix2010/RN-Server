# ADR-0018：邀请关系作为基础服务

状态：Proposed（2026-09-15，经四路对抗评审修订）

## 背景

App 里「邀请返佣」三处入口一直是占位：首页快捷格无 `onPress`，个人中心两行点击弹空态 toast 且写死"已邀请 12 人"。产品要求补齐，但把邀请关系与返佣一起设计会让关系随返佣规则改动而改动——关系是一次性、不可变、需要长期可追溯的事实，返佣规则会反复改。

本期只做关系层：回答"我的邀请码是什么、谁邀请了我、我邀请了谁"，不涉及任何金额。完整设计在 RN-App `docs/design/referral-graph-2026-09-15.md`，字段语义在 `docs/database/REFERRAL_SCHEMA.md`。

## 决策

### 存储

- **不建新表，四列并入 `wallet_user`**：`invite_code`、`inviter_user_id`、`invited_at`、`invite_source`。一个被邀请人最多一个邀请人、一次性不可改，是严格 1:1 属性；单独建表等于给 `wallet_user` 做 1:1 拆分，还要自己维护"最多一行"这个约束，而列上的 NULL 天然表达它。绑定事件进 `audit_events`，租户配置进 `app_configs` 的 `mobile-bootstrap`，直接下级数由索引 `COUNT(*)` 得出而不做冗余计数列。

  依据**不是** `AGENTS.md` 里"只有一个写方的运行状态可合并"那一条——`wallet_user` 有三个写方（登录 upsert、绑定、链上索引器的批量 UPDATE），不满足它。合并的依据是 1:1 属性，并发代价由下面的串行化决定单独付。

- **拆表的临界点写进文档**：关系需要任何非 1:1 属性（活动 id、等级、分成比例、结算状态）、需要历史或版本、或需要第二个邀请维度时就拆。**返佣立项几乎必然触发第一条。** 不写这句，默认路径就是继续往登录热表上堆 NULL 列。

- **`invite_code` 永久可空，且不进登录的 INSERT**。登录语句是 `INSERT ... ON DUPLICATE KEY UPDATE`（`wallet_auth.go:248`），MySQL 对任意唯一键冲突都触发 ON DUPLICATE 分支：把 `invite_code` 放进去，抽到的码撞上他人的码时会去更新**那一行**（实测 `address` 被改、`ROW_COUNT()=2`），随后按 `address_key` 查不到自己 → 500；而且 ODUP 不抛 1062，"碰撞由唯一键兜底后重试"这个策略根本无从捕获。改成 `NOT NULL` 则回滚到旧二进制后旧 INSERT 不带该列，strict 模式实测 ERROR 1364，**老用户也登不上**；`DEFAULT ''` 又让并发新用户在唯一键上互撞。

  因此码由注册事务里一条独立的 `UPDATE ... WHERE invite_code IS NULL` 赋予，它抛真正的 1062，可捕获换码重试。"人人有码"由事务保证，不由列约束保证。副作用是回滚安全。

- **迁移四个独立版本，且不做 contract 步**：加可空列 → 幂等回填 → 加索引与 CHECK → 结束。把加列与唯一键写在一条 ALTER 里实测必然失败（已有行填 `''` 后唯一键冲突），且失败后不幂等，重启报 `Duplicate column name`，**服务永久起不来，必须人工改库**。用既有的 `addColumnIfMissing`（`migrations.go:91`）。

### 关系图

- **不存层级深度**：`depth` 可派生，且某人绑定上级后整棵子树的 depth 都要改，冗余列必然失同步。防环靠沿 `inviter_user_id` 上溯，上界是**服务端内部常量且取个位数**——本期没有任何功能按层级分叉，做成配置项等于给运营一个无法判断的旋钮。

- **绑定按租户 `GET_LOCK` 串行化**。条件更新只保证"最多一个邀请人"，**不保证无环**：默认 REPEATABLE READ 下事务内普通 SELECT 走快照，A、B 同时互扫对方的码时两边上溯都看不到对方的写入，最终改的是不相交的两行，**零锁冲突、零死锁**，环就此永久留下（关系不可解绑）。用 `db.Conn()` 钉住连接取锁，照 `simplified_releases.go:358-368` 的成例；不要照抄 `migrations.go:977-980`（在池上取锁、可能在另一条连接上释放）。

  不选逐跳 `SELECT ... FOR UPDATE`：它会与索引器按 Go map 随机顺序的批量 UPDATE（`indexer/store.go:370-382`）形成交叉加锁顺序，必然死锁。绑定一生一次，串行化零成本。

- **上溯用应用层循环**：MySQL 是 8.x（`docs/ARCHITECTURE.md:22`、ADR 0003，且 `wallet_users_admin.go:322` 已在用 `LEFT JOIN LATERAL`），递归 CTE 可用；选循环的理由是可测、边界显式，不是版本限制。

- **三列同生共死由 CHECK 约束强制**，不只是应用层约定。否则补录漏写一列就会产出 `inviter_user_id` 非空、`invited_at` 为空的行，它在自己上级的下级列表里**永久不可见**（键集分页的游标条件把 NULL 全排除），`total` 也会对不上。

- **关系一次性、不可解除**：管理端只提供补录，不提供解绑。后续返佣账本会引用关系，关系可改等于历史可改。

- **封禁不改变已有关系**：封禁只影响能否**新建**关系。已绑定的双方无论之后是否被封，关系照常存在、照常展示；管理端能看到双方的封禁状态，用户看不到对方的账号状态。解封无需复原，因为从未改变。

### 接口与安全

- **移动端接口不返回任何地址派生值**。`shortenAddress(addr, 6, 4)` 输出 8 个 hex nibble = **32 bit**，候选集 10⁶ 时期望碰撞 2.3×10⁻⁴——对任何现实候选集，"脱敏"地址就是唯一键，拿去公链索引器一查就还原出完整地址、余额与交易史。因此：邀请人身份用**邀请码**表示（用户本来就拿着那个码），下级用 `HMAC(tenant_secret, viewer_id‖invitee_id)` 的 per-viewer 别名，免登录的 `codes/:code` **只返回 `{valid}`**。

  这同时把该接口从"码 → 地址指纹的 oracle"降级为"码是否有效"。盲枚举本来就不可行（命中率 N/1.1×10¹²），真实风险来自返回内容而非尝试次数。

- **归一化只在服务端做**：trim、全角、大小写、分隔符、Crockford 的 `I`/`L`→`1`、`O`→`0` 映射全部在服务端一处完成（`U` 不映射，它被排除在字母表外，出现即输错）。各端各自 trim 就是第二份真相。格式非法（`REFERRAL_CODE_MALFORMED`，422）与码不存在（`REFERRAL_CODE_UNKNOWN`，404）必须是两个错误码——前者是用户输错、后者是码无效，文案完全不同。

- **管理端补录是全文影响最大的入口**，它豁免绑定窗口（那正是补录存在的意义），而窗口是"存量用户能被追溯挂多少"的唯一上界；叠加不可解绑，一次脚本化误用永久不可回滚。当前管理凭证是全平台唯一一份（`config/config.go:123-124`），租户隔离只在 Host 头这一层（`server.go:224`），管理端除登录外全线无限流。在不引入 RBAC / 双人审批的前提下，补录必须同时具备：`decodeAdminAction`（`confirm=true` + `reason`）、`expectedInviteeState` 乐观锁、租户日配额（形态照 `diagnosticTenantPerDay`）、对 `x-admin-key` 通道直接 403。

- **失败也要留痕**：全仓无访问日志中间件（`gin.New()`，`server.go:130`），`problem()` 不写日志，审计只在成功路径写。照原样实现的话，失败绑定与 100% 的枚举流量在应用层零记录，连"是否正在被枚举"都无数据可判。因此 `codes/:code` 未命中与 `bind` 的各类拒绝各记结构化 `slog.Warn`（不记完整邀请码），触发限流额外写 `audit_events`。

- **绑定需要用户明确确认**：深链带来的邀请码在登录后不自动提交，先弹 Dialog。用户在深链里同意的是"登录"，不是"永久挂在一个陌生人名下"。`PRODUCT_EXPERIENCE_STANDARD.md` §5 规定 Toast 只用于低风险瞬时反馈、Dialog 用于高风险确认。深链暂存有效期 30 分钟，不是绑定窗口的 7 天——后者等于留一个攻击者可控的输入，在用户早已忘记的某次登录上生效。

### 滥用

- **一期不做判定，但必须留证。** 原结论"一期关系没有金钱价值，拦截收益为零"漏算了时间：攻击者的收益在返佣上线之后，而关系是在一期以零成本预置的。注册链路三步全部免鉴权、零限流（`installations/register`、`auth/nonce`、`auth/verify`），**3 个 HTTP 请求一个账号**。而"返佣上线时追溯清理"在结构上做不到——关系不可解绑，封禁也不清除 `inviter_user_id`，返佣模块只能另建抑制名单，正是本 ADR 花力气避免的第二份真相。

  因此本期做三件事：绑定时把风控信号（注册 IP/ASN、注册时间、installation 复用、双方注册间隔）落进 `audit_events.summary`；给 `installations/register` 与 `auth/nonce` 加限流并**与本设计同窗口上线**；在本 ADR 写明返佣上线前的存量处置由抑制名单承担，与关系表的优先级提前约定。

- **设备标识仍不参与判定**（沿用 ADR 0014 §3），本期也不做 `sameDeviceAsInviter` 标记——它没有消费方。上面的信号采集是留证，不是判定。

### 客户端

- **一期不做 App 内扫码**：二维码内容是邀请链接，任何相机扫到都经 App Links 落回 App，能力不缺。而 `AddressScanner` 并不通用（硬编码 7 个 `send.*` 键，相机权限系统文案写死 "scan wallet address QR codes"），通用化是原生 Manifest 级改动。少一个入口也让 `invite_source` 不必区分"扫码"与"点链接"——两者本来就是同一条深链路径。

- **App Links 路径写带尾斜杠的 `/app/invite/`**：现有写法是 `pathPrefix`，前缀匹配会把 `/app/invitexyz` 一并吃进来。

## 替代方案

- **独立 `referral_relation` 表**：为将来可能的关系属性预留。否决——本期严格 1:1，预留的是想象中的需求；真需要时拆表是一次可控迁移，而现在拆表要立刻承担一次 JOIN 和一个自己维护的唯一约束。
- **`invite_code` 从 `user_id` 派生**：省掉生成与碰撞处理。否决——可枚举，且暴露租户用户规模。
- **存 `depth` 并在绑定时递归更新子树**：让按层级查询 O(1)。否决——子树可能很大，而本期没有任何按层级的查询。
- **逐跳 `SELECT ... FOR UPDATE` 防环**：不引入额外的锁原语。否决——与索引器的随机顺序批量写必然死锁。
- **永远允许补绑**：让存量用户也能被发展。否决——返佣上线后会产生"老用户突然有了上级"的分成争议。存量用户只能走管理端补录，这是有意的。
- **邀请人被封禁时隐藏其下级关系**：看起来更干净。否决——关系是事实；隐藏会让被邀请人以为数据丢了，也会让日后对账出现看不见的行。
- **下级列表返回脱敏地址**：实现最省事。否决——32 bit 等同唯一键，等于提供去匿名化接口。

## 安全边界

- 移动端响应不含任何地址派生值；管理端返回完整地址（有权看）。
- 免登录的 `codes/:code` 只返回布尔值；与落地页 `GET /app/invite/:code` **共用同一个限流计数器**（两者是同一个 oracle，分开计等于限流白做），未命中另计更严的子配额。
- 限流器复用 `diagnosticIPLimiter` 形态，**在内存里、按实例计数，只挡单一来源**——如实记录，不假装它是强闸。
- 租户隔离：所有查询与写入带 `tenant_id`；邀请码唯一性是租户内的，跨租户同码互不影响。
- 当前阶段无 RBAC 与双人审批（沿用既有产品决策），补录的约束靠 confirm + 乐观锁 + 日配额 + 禁用 `x-admin-key` 通道。

## 待核实

- 线上 `ADMIN_IP_ALLOWLIST` 的范围（amos 同机既跑打包又跑后端）。
- 是否存在未登记 `release.android` 的租户——那些租户的邀请链接会落在 Android 校验失败的状态。
- 上游 nginx 访问日志的留存策略。
- 生产库 `wallet_user` 的真实 collation（测试库实测 `utf8mb4_0900_ai_ci`，唯一键本身大小写不敏感，与归一化要求一致，但 DDL 未显式指定）。
