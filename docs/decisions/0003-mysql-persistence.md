# ADR-0003：使用 MySQL 持久化平台配置与发布数据

- 状态：Accepted
- 日期：2026-08-24

## 背景

发布、审计和移动端配置最初使用内存数据与代码常量，只能演示接口，服务重启后无法保证运营数据连续。当前项目基础设施明确使用 MySQL 8.x。

## 决策

RN-Server 使用 Go `database/sql` 与 go-sql-driver/mysql 连接池连接 MySQL。最大连接、最大空闲连接、连接生命周期、空闲回收时间和查询超时全部通过环境配置，并为共享数据库部署采用较小的生产池。

当前数据库包含：

- `app_releases`：Release、Artifact、Rollout 及状态；
- `audit_events`：发布和配置操作审计；
- `app_configs`：国际化、主题、Feature Flag 和升级策略 JSON 配置。

创建发布和状态转换写入 MySQL，发布状态与审计在同一事务中提交。`/health/ready` 必须完成 MySQL ping。生产应用启动不执行 DDL；schema 通过受控、只向前的迁移步骤初始化或升级，避免共享 MySQL 出现元数据锁与重启风暴。

本阶段按产品要求不实现 RBAC 和双人审批。管理接口继续使用本地管理员身份适配器、操作确认、reason 和审计；认证授权和审批将来作为独立模块接入。

## 备选方案

- 继续内存 Repository：开发简单，但无法重启恢复，也不能作为管理控制面的事实源。
- PostgreSQL/Prisma：原蓝图的默认建议，但与当前指定基础设施不一致。
- MongoDB：JSON 配置方便，但发布唯一约束、状态事务和审计查询更适合关系数据库。

## 后果

- 本地和部署环境必须提供 MySQL；测试自动使用带 `_test` 后缀的数据库。
- 密码只通过环境变量注入，`.env` 不入库。
- 本地隔离初始化可显式启用自动建表；生产必须采用独立、版本化、只向前的迁移工具。
- JSON 列适合当前配置整体发布；需要字段级查询和独立生命周期时再拆表，不提前过度建模。
