# ADR-0023：租户控制台的邮箱二次验证

状态：Accepted（2026-09-27）

表：`docs/database/ADMIN_ACCOUNTS_SCHEMA.md`（`admin_sessions.second_factor_at`，迁移 62）；接口：`contracts/openapi.json`；实现：`internal/api/second_factor.go`；上下文：ADR-0021、ADR-0022，设计 tenant-console-accounts-and-sso-2026-09-25 §4.5。

## 背景

租户控制台的成员用统一登录（认证中心）进来。认证中心不告诉我们对方怎么登录、何时登录的，统一账号的口令泄露，就等于进了这个租户的控制台，能换签名密钥、推送凭据、放量发版。设计 §4.5 原计划用 RN 自己的 TOTP 做二次验证，用户 2026-09-25 要求先定设计再实施；2026-09-27 定为**邮箱验证码**，不用验证器 App（ADR-0022 之后 RN 已经有发信能力）。

## 决策

1. **只对租户会话**。平台会话（`ADMIN_USERNAME`、管理密钥）不用：它没有邮箱，口令只在平台手里。
2. **验证码发到成员自己登记的邮箱**（平台管理员建号时填的 `tenant_admin_accounts.email`），不是统一账号的邮箱：统一账号被盗时，它的邮箱可能也在对方手里；登记邮箱是另一条独立的渠道。
3. **验过的是会话**：`admin_sessions.second_factor_at`，15 分钟内有效；换一个会话（换浏览器、重新登录）要重新验。验证码只属于发码的那个会话。
4. **敏感操作**（`requireSecondFactor`，挂在路由上）：签名密钥（导入、生成、导出密文）、OTA 与 bootstrap 签名密钥、推送凭据增删、App Manager Key 增删、发布身份、存储凭据、切换 iOS 交付方式、发版与热更新的放量 / 回滚 / 删除。成员管理本来就只有平台管理员能做。不够 15 分钟返回 403 `SECOND_FACTOR_REQUIRED`，控制台弹框验证后重试。
5. **待绑定的成员发起绑定前也要验**：初始口令泄露时，拿到口令的人收不到本人邮箱的码，抢不先绑。
6. **验证码的存法与限流沿用绑定验证码**（进程内存；10 分钟、用一次、错 5 次作废；每账号 1 分钟 1 次、1 小时 5 次，每 IP 1 小时 20 次）。
7. **没配发信就做不了敏感操作**，返回 503 `MAIL_NOT_CONFIGURED`，不退回「不验证」（AGENTS.md「不写回退」）。
8. 发码与验证都写审计（收件人掩码，不含验证码）。

## 后果

- 上线前平台管理员要先配好发信（ADR-0022），否则成员既绑不了，也做不了敏感操作。
- 登记邮箱填错或本人收不到，只能由平台管理员改（目前要改库，成员页还不能改邮箱）。
- 防不住登记邮箱本身也被盗的情况；以后认证中心能回传认证方式与时间，或者要更强的因素（TOTP、通行密钥），在同一个 `second_factor_at` 上加即可，敏感路由不用再改。
- RN-Server 单实例：验证码在进程内存里，重启后要重发；`second_factor_at` 在库里，重启不影响已验过的会话。
