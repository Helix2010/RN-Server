# ADR-0024：控制台账号由外部系统维护，RN 只鉴别

状态：Accepted（2026-09-27）

完整设计：`docs/design/console-accounts-external-maintenance-2026-09-27.md`（下称「设计」）；表：`docs/database/ADMIN_ACCOUNTS_SCHEMA.md`（迁移 64）；接口：`contracts/openapi.json`；实现：`internal/api/tenant_accounts.go`、`cid_login.go`、`admin_session.go`。取代 ADR-0021 的第 4、5、7 条与 ADR-0023 的第 5 条。

## 背景

ADR-0021 让 RN 自己管账号：平台管理员在控制台建号、发初始口令，本人登录后绑定统一认证账号，之后在控制台停用、解绑重置。2026-09-27 平台管理员也进了这张表（`scope` 列，迁移 63），同一套流程还加了建号命令。

用户 2026-09-27 决定不要这一套：**不要本地口令，也不要本地账号**。账号由统一登录的平台端分配，直接写进 `tenant_admin_accounts`；是平台管理员还是租户成员，由别的系统管理维护，RN 不管数据在哪里维护，只按自己的规则鉴别。

## 决策

1. **`tenant_admin_accounts` 由外部系统写**：`scope`、`tenant_id`、`idp_subject`（小写 uuid）、`email`、`display_name`、`status`（`active` / `disabled`）。RN 只写 `last_login_at`。数据库用 CHECK 挡住写错的行：大写或不是 uuid 的账号 id、`scope` 与 `tenant_id` 不一致、不认识的状态、不像邮箱的邮箱。
2. **统一登录回调的规则**：同一个统一账号同时有平台记录与任何租户记录 → 拒绝并记日志（`identity_conflict`，不猜用哪个身份）；只有平台记录 → 平台会话；有当前域名租户的记录 → 租户会话；其余 → `no_access`；选中的记录不是 `active` → `disabled`。不自动开户。
3. **每个请求回表**：账号要是 `active`，按会话类型查得到（平台会话查 `scope='platform'`，租户会话查会话租户），`idp_subject` 等于登录时记在会话上的那个（`admin_sessions.idp_subject`）。外部系统停用、删除、换人、改身份，都在下一个请求生效。
4. **删掉**：账号的初始口令登录、`pending_bind` 与 `BIND_REQUIRED`、绑定流程与绑定验证码、控制台里的建号 / 停用 / 重置、建号命令、登录名。控制台只保留只读列表，只给平台管理员看。
5. **不变**：会话的平台 / 租户隔离、Origin 检查、统一登录接入方式、控制台里的登录页、邮箱二次验证（验证码发到账号记录的 `email`）。环境变量账号仍按平台账号设计的「发布 2」删除，时间点改为外部系统写好第一条平台管理员记录并验收之后。

## 后果

- **能写这张表的人就能开平台管理员**，连二次验证用的邮箱也是他写的。外部系统的数据库账号只给这张表的读写（设计 §3 的 GRANT），口令只放在外部系统里。
- 账号变更的审计由外部系统负责，RN 不再记 `*_create` / `*_disable` / `*_reset` / `*_bind`。
- 身份冲突只在登录时检查；已登录的平台会话要等会话过期，需要立刻踢人时停用那一行。
- 迁移 64 删掉过不了新约束的行（没绑定过的、账号 id 不合规的），连同它们的会话。线上迁移前只读核对过，只有一个已绑定的成员，不受影响。
- 外部系统停摆不影响登录（RN 只读本地表）；认证中心停摆时照旧谁都登不进。
