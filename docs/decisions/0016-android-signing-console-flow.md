# ADR-0016：Android 签名与打包配置在控制台上合并，并支持服务端生成签名密钥

状态：Accepted（2026-09-12）

## 背景

出一个正式包要三块配置：签名密钥（`build.keystore`）、正式包身份（`release.android`：包名 + 证书 SHA-256）、打包参数（`build.android`：应用名 / scheme / 配置地址 / google-services.json / 仓库目录）。它们分在控制台两页——「打包配置」与「Android 签名与身份」。

核对现状后发现的问题不是"多点一次鼠标"：

- **证书指纹被做成一个自由输入框。** 指纹不是可以独立决定的值，它是 keystore 里那张证书的摘要。做成输入框就有了一个可以填错的地方，而填错不当场报错——要等到上传产物时才 `RELEASE_SIGNER_MISMATCH`，报错看不出是这里抄错了一位。
- **提示写的是 `apksigner verify --print-certs`。** 那要求你已经有一个 APK。新租户第一次配的时候没有，这条指引对首次配置是死的。
- **全站没有一个地方说 keystore 怎么来。** `build-keystore seal` 假设它已经存在，新租户就卡在这一步。
- **`seal` 算得出指纹却不输出它**，于是人必须再跑一次 keytool 把 64 位十六进制抄进另一个页面的表单。
- **google-services.json 的包名不校验。** 它必须等于 `release.android` 的包名，否则 Firebase SDK 初始化时不注册——构建成功、APK 能装、没有任何一步报错，只有推送在用户手机上静默失效。两块配置分在两页时，这条跨页约束**没有地方可以校验**。
- 仓库目录服务端本来就有默认值（租户 slug），前端却当必填；构建分支固定 `main`，却占着一个只读输入框。

## 决策

- **合并成一页「Android 打包与签名」**（导航 id 仍是 `build-config`）。存储上仍是三条各带乐观锁的记录，所以页面上是三个保存动作而不是一个大表单——把三条塞进一次提交，只会让"其中一条冲突"变成半保存状态。页面开头用一张图说明因果链，因为这条链上任何一环对不上，失败都发生在很后面。

- **`POST /v1/admin/build-keystore/generate`：服务端生成签名密钥。** 管理员只填包名、证书名称、alias、密钥长度、有效期和封装口令。

  它**不削弱**"服务端打不开已存密钥"这条性质：生成出来立刻用管理员的封装口令 scrypt 封盒，服务端此后只有盒子。差别只在生成的那一刻——明文私钥在服务端进程内存里存在过。今天那是"从来没有"。所以：
  - 离线那条路完整保留，并补上 `build-keystore create`（生成 + 封装一步到位），不接受这点暴露的场景走它；
  - 明文 keystore 与随机生成的 store 口令只在这一次响应里返回，不落盘、不写日志、不进审计；界面强制先下载才能关掉那一屏；
  - store 口令由服务端随机生成而不是让人想一个：它被封在盒子里，打包机从盒子里读，没有任何人需要记住它。

- **指纹永远由密钥那一步写入，两条记录在一个事务里。** 生成走 `generate`；离线走 `PUT /v1/admin/build-keystore`，新增可选的 `signerSha256` + `packageName` + `releaseIdentityExpectedVersion`（三项要么都给要么都不给，只给一半判 400 而不是静默忽略）。手工登记的入口保留但要显式点开——keystore 不在本系统里管时（从别处迁入的 App）确实需要。分两步做会留下"密钥换了、pin 还是旧的"这个中间态，而那个态下所有上传都被判 `RELEASE_SIGNER_MISMATCH`。

- **keystore 用自己拼的 PKCS#12，不用现成的编码库。** go-pkcs12 与 x/crypto/pkcs12 都不写 `friendlyName` 属性，Java 读到没有它的条目就按序号编号——别名会变成 `1`，而 Gradle 拿 `keyAlias` 去找条目。别名对不上的表现是构建跑到最后一步才失败。格式与 keytool 一致（私钥 PBES2/PBKDF2-HMAC-SHA256 + AES-256-CBC，证书明文，整体 SHA-256 MAC），并有一条测试真的用 keytool 打开产物、核对别名与指纹——自己解自己写的格式只能证明前后一致，证明不了 Java 读得懂。

- **google-services.json 的包名一致性三处校验**：选中文件的那一秒（浏览器）、保存打包配置时（`GOOGLE_SERVICES_PACKAGE_MISMATCH`）、排队构建时（`tenantManifestFor`）。第三处不是冗余：两块配置可以按任意顺序配，先传文件后登记包名时，保存那一刻还没有包名可比。

- **仓库目录留空即用租户 slug**（服务端本来就这么回退），和构建分支一起收进「高级」。让人手抄一个系统已经知道的名字，只是多一个能抄错的地方。

## 顺带修掉的两个既有缺陷

- `cmd/build-agent` 里"拒绝 RN 公开 debug 密钥"的常量填的是那把密钥的 **SHA-1 补零凑到 64 位**，而比对的是 SHA-256——两者永远不相等，这道闸从来没有生效过。一条恒假的断言比没有断言更坏，因为它让人以为这里已经拦住了。值改为与服务端共用 `androidkeystore.PublicDebugSignerSHA256`，并加了一条会真的失败的回归测试。
- `PUT /v1/admin/build-keystore` 的回参少 `updatedBy` / `updatedAt`，而管理端读写用同一个 schema——**从控制台上传签名密钥其实一次都没成功过**：服务端存下了，界面报错。回参改成与 GET 同形，并加了一条比对两者键集的测试。

## 代价

- 服务端生成这条路上，明文私钥会短暂进入服务端进程内存。攻陷服务端的人拿不到任何**已存**的密钥（它们用服务端没有的口令封着），但能截获在攻陷窗口内生成的那些。选项是显式的，界面上直说，离线那条随时可用。
- 生成出来的 keystore 只有一份，在管理员手上。丢了它或丢了封装口令，这个 App 就再也发不出能覆盖安装的新版本——和自己用 keytool 生成时的处境相同，但控制台让这件事变容易了，所以那一屏是强制的。
